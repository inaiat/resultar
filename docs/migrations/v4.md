# v4: Task workflows and the Async compatibility subpath

v4 makes `ResultTask` the default for new asynchronous workflows and provides explicit eager
compatibility imports through `resultar/async`. Existing main-entry Async exports, Result async
methods, tagged-error helpers, and Task bridges remain supported for gradual migration.
Package versions change through the Changesets release workflow.

For a learning path from Result to Task, Clock, retry and Fibers, read
[gradual adoption](../gradual-adoption.md). Migration can happen one workflow at a time;
an eager boundary can keep its current contract while imports move to the compatibility subpath.

## Entry points and installation

```sh
pnpm add resultar
```

One installation includes both entry points. Results, Tasks, AbortError, tagged errors and Retry
policies keep one identity shared with the compatibility subpath. Root Async imports continue
to work; prefer the subpath when writing explicit eager compatibility code.

```ts
import { Result, ResultTask, createTaggedError, ok } from "resultar";
import {
  ResultAsync,
  asyncAndThen,
  asyncMap,
  gen,
  fn,
  safeTry,
  tryResultAsync,
} from "resultar/async";
import type { StrictResultAsync } from "resultar/async";
```

`ResultAsync`, `StrictResultAsync`, and all Async-specific factories and helpers, including
`okAsync`, `errAsync`, and `tryResultAsync`, are deprecated APIs implemented in
`packages/resultar/src/resultar-async`. Async-only types are declared there; core modules that
previously declared them retain type-only re-exports. Main-entry exports retain the same classes
and helper identities.
The compatibility subpath preserves eager, single-execution behavior: factories start immediately,
and repeated awaits observe the same Promise of a core Result. This does not make a
requirement-free Task awaitable.

## Supported APIs and preferred new code

| Supported API | Preferred new code |
| --- | --- |
| Deprecated root `ResultAsync`, `StrictResultAsync`, `DisposableResultAsync` and Async option types | Existing imports still work; prefer `resultar/async` for eager compatibility |
| Deprecated root `tryResultAsync`, Promise/callback wrappers, `okAsync`, `errAsync`, `unitAsync`, `runPromise` | Existing imports still work; prefer the subpath, or Task factories and runners for new workflows |
| Deprecated `tryAsync` / `tryCatchAsync` | Still work; prefer `tryResultAsync` within eager code |
| `Result.gen(async function*)` / async `Result.fn` | Still support eager execution; prefer `ResultTask.gen` / `fn` for new lazy workflows |
| Async `safeTry` and `SafeTryAsyncOptions` | Still available from the main entry and subpath; retain final-Result returns |
| `result.asyncMap(f)` / static form | Still work; free `asyncMap(result, f)` / curried forms make eager imports explicit |
| `result.asyncAndThen(f)` / static form | Still work; free `asyncAndThen(result, f)` / curried forms are also available |
| `TaggedErrorClass.errAsync(props)` | Still works; `errAsync(new TaggedErrorClass(props))` is an explicit eager alternative |
| Task static/instance `toResultAsync` | Still works; prefer `ResultAsync.fromTask(task)` in new eager code |
| Deprecated Task `succeed` / `fail`, `mapError`, `flatMap`, `catchAll` | Still work; prefer `ok` / `err`, `mapErr`, `andThen`, `orElse` |
| Task retry options and legacy match handler objects | Still work; prefer `Retry.policy(...)` and `{ ok, err }` |
| Existing eager workflow inside a Task | `ResultTask.fromResultAsync(existingOrFactory)` accepts structural `PromiseLike<Result>` |

Core `Result.gen` / `Result.fn` and free subpath `gen` / `fn` support sync and async bodies
with modern plain success returns. Deprecated `safeTry` keeps the separate legacy contract
requiring a final Result, including async generators. `safeTry` is not an identity alias of
modern `gen`. No Result or Task prototype is patched by importing `resultar/async`.

`safeTry` and its legacy types have one implementation in `src/resultar-async`;
the root and previous module paths re-export it for compatibility. Task workflows
use `ResultTask.gen`; there is no `ResultTask.safeTry` alias.

## Choose the execution boundary explicitly

Task is lazy and repeatable. Prefer `task.runResult()`, `task.runPromise()`, `task.runExit()`, or
`task.runFork()` for each execution. The static forms, such as `ResultTask.runResult(task, options)`,
remain supported and equivalent. Both forms accept the same options and enforce required services;
pending scope release errors join their error types (`E | ScopeError<R>` internally).
Each call starts fresh work. Task has no `.then`; `await task` leaves it unexecuted,
and there is no public `task.run()` runner.
Providing services and closing scopes leaves a Task. Task `map` is synchronous;
compose Promise work with `andThen` and `ResultTask.tryPromise`.

The core inbound bridge is structural and accepts `PromiseLike<Result<T, E>>` without
importing `ResultAsync`. `fromResultAsync(existing)` reuses an already-started execution;
its factory form creates fresh work for each Task run. Request helpers continue to return
eager Async from `resultar/async`, so put a request call inside this factory when repeating it.

```ts
import { ResultTask } from "resultar";
import { ResultAsync, gen, tryResultAsync } from "resultar/async";

const legacyLoad = () =>
  gen(async function* () {
    return yield* tryResultAsync(
      () => client.load(),
      (cause) => new Error("Load failed", { cause }),
    );
  });
const task = ResultTask.fromResultAsync(() => legacyLoad());
const result = await task.runResult();
const eagerOnce = ResultAsync.fromTask(task);
```

`ResultAsync.fromTask(task)` immediately starts one requirement-free execution and
memoizes it. Provide all services and close required scopes before crossing that
outbound boundary. Prefer explicit Task runners for new application boundaries.

`runResult` converts a simple typed failure to Err and can reject defects,
interruption or composite causes. `runExit` preserves all causes as values without rejection;
`runPromise` resolves the success value or rejects any failure. `runFork` starts a root fiber
immediately and returns its `FiberHandle`. The
Async instance `match`, `matchTags`, `matchTagsPartial` and `unwrapOr` keep native Promise
terminals returning raw handler output. Their static/direct/curried forms return composable
`ResultAsync<Out, never>` values; Task matching stays a lazy operator.

## Retained spellings and observation

Prefer Task's `ok`, `err`, `mapErr`, `andThen` and `orElse`. Deprecated `succeed` / `fail`,
`mapError`, `flatMap` and `catchAll` retain their original signatures and behavior. Object
handlers also retain `{ ok, error }` and `{ onSuccess, onFailure }` alongside `{ ok, err }`.
Retry accepts portable policies and the older options shape; preserve each callback contract.
Core default / `try` / `tryCatch`
still alias the synchronous `tryResult` helper. `safeUnwrap` remains available for
synchronous Result composition, with `yield* result` preferred.

Result and compatibility Async `tap` / `tapError` remain best-effort observation aliases;
callback failures are swallowed and the original outcome is preserved. Prefer
`inspect` / `inspectError`. Only Task `tap`, `tapError`, `tapCause` and `tapBoth`
compose fallible Task side operations. Async `map`, `mapErr` and `filterOrElse` keep
Promise-aware callback contracts independently of Task's synchronous transforms.

## Type safety improvements

Tagged recovery tables remove an error only when its handler is required and
defined in every possible table variant. Optional handlers keep the error in `E`;
recovery outputs include all possible handler returns. Code that relied on errors
being incorrectly erased may need to handle those errors explicitly.

New concurrent operations can produce `Cause.Parallel`. Consumers that inspect
Cause with an exhaustive switch should handle this branch alongside Sequential.
Existing sequential workflows retain their execution behavior.

## Matching at native HTTP boundaries

On `Result<T, E>`, `match`, `matchTags`, `matchTagsPartial`, and `unwrapOr` return
the unwrapped output `Out` directly. On deprecated `ResultAsync<T, E>` instances, they return
native `Promise<Out>` terminals. Async static/direct/curried forms instead wrap the output
in `ResultAsync<Out, never>` for further composition. On `ResultTask<T, E, R>`, they remain lazy operators
returning `ResultTask<Out, never, R>`; use `folded.runPromise()` for the
unwrapped output, or match on the Result returned by `runResult`.

Existing Result and Async `matchTagsPartial` instance callbacks retain their full
error-union parameter for compatibility. The newer functional forms narrow
fallbacks to errors not guaranteed to have a handler. Optional or possibly
undefined handlers never erase a possible fallback error.
The special `Error` handler retains its existing runtime catch-all behavior.

`Match.context<Input, [context: Context]>()` compiles a function `(input, context)`
whose handlers receive `(narrowedInput, context)`. It avoids duplicating the
matched input in selector arguments. Native response/status unions are retained.
`Match.fn(selector)` keeps its existing selection and original-arguments contract.

Finite object patterns subtract combinations of literal fields, including nested
fields. Arbitrary predicates, partial refinements, optional patterns and open
arrays remain conservative. Exhaustive-call diagnostics expose `missingCases`.

## Task concurrency and policies

`forkChild` starts a child only during execution. Children belong to the enclosing
scope; closing it interrupts active children and awaits them before releasing
parent resources. `Fiber.join` propagates the child result. `Fiber.interrupt`
awaits completion and returns its full Exit. Unobserved child failures remain
tracked in the scope requirements and are included at closure.

`race` returns the first success; if both fail it preserves their parallel causes.
`raceFirst` returns the first outcome. Both interrupt remaining children and await
their finalizers. `timeout` uses a typed timeout error and the same cleanup rules.
Cleanup failures are preserved rather than being replaced by the winner.

```ts
import { ResultTask, Retry } from "resultar";

const resilient = loadUser(id)
  .retry(Retry.policy({ times: 2, delayMs: 100, backoff: 2, jittered: 0.2 }))
  .timeout(2_000, () => new UserTimeoutError());

const result = await resilient.runResult();
```

`times` counts retries after the initial attempt. Retry applies only to simple
typed failures and closes each attempt scope before the next attempt. Defects,
interruption and composite failures are not retried. The optional `while` callback
filters retryable errors.

`all` preserves tuple/record shape; `forEach` preserves input order. Both default
to sequential execution and accept `{ concurrency: number | 'unbounded' }`.
Failure stops scheduling, interrupts active children and awaits their cleanup.
`validateAll` gathers typed errors in input order; defects and interruption stop it.

Cancellation remains cooperative. A task/driver that ignores abort, or a finalizer
that never settles, can keep the run pending. Timeout is not a hard deadline for
cleanup. `runExit` preserves `Parallel` and `Sequential` causes; `runResult`
rejects composite failures with ResultTaskCauseError.

## Deterministic time

Run options accept `clock?: TaskClock`; the default is `Clock.live`. Tests can
advance `Clock.virtual()` without wall-clock timers. Retry jitter uses the same
clock's random source, which can also be deterministic.

```ts
const clock = Clock.virtual();
const pending = task.runResult({ clock });
await clock.advanceBy(2_000);
const result = await pending;
```

## Checker support

The checker recognizes both `safeTry` and `Result.gen` using the existing
`noAwaitInSafeTry`, `noTryCatchInSafeTry` and `yieldStarInSafeTry` options and their
original rule IDs. Delegated `yield*` expressions consume their Results, and the
new task collection/fiber operators are recognized as consumers. MatchMatcher
hover shows input, remaining cases and matched output. `preferResultAsync` remains
available for deliberately retained eager application contracts; it is not a
requirement to replace new Task APIs with the deprecated facade.
