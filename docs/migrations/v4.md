# Next major: additive adoption guide

The next major preserves the existing composition, generator, observation and
export APIs. New Match and task runtime capabilities are opt-in. Package versions
change through the Changesets release workflow.

For a learning path from one `Result<T, E>` function to `ResultTask`, `Clock`, retry,
and Fibers, read [gradual adoption](../gradual-adoption.md). These notes cover changes
between releases; adopting the task model is optional and can happen per use case.

## Migrate one workflow at a time

`ResultAsync<T, E>` and `ResultTask<T, E, R>` now share a single unified implementation:
`ResultAsync<T, E>` is `ResultTask<T, E, never>` (a `ResultTask` with no pending requirements),
and `ResultAsync` at runtime is an alias for `ResultTask`. Any task with `R = never` implements
`PromiseLike<Result<T, E>>` and can be `await`ed directly, while tasks with pending service or
scope requirements (`R !== never`) block direct `await` until requirements are provided or the
task is passed to `ResultTask.runResult` / `runExit` / `runPromise` / `runFork`.

Keep synchronous domain functions returning `Result` and requirement-free async
contracts returning `ResultAsync`. A task can compose both with `yield*` in `ResultTask.gen`
or `Result.gen`, or pass the active `AbortSignal` into a factory via
`ResultTask.fromResultAsync((signal) => adapter(signal))`.
Wrapping an already-started `Promise` with `fromPromise` captures that execution rather than making
it repeatable; use `tryResultAsync` or `ResultTask.tryPromise` so each task run and retry creates fresh work.

`ResultTask.toResultAsync(task)` narrows/returns a requirement-free `ResultTask<T, E, never>` as
`ResultAsync<T, E>`. Awaiting a `ResultAsync` uses the default runtime (`runResult`); use `runResult`
or `runExit` directly when supplying `services`, a custom `clock`, `signal`, or `scheduler`.
`runResult` handles a simple typed failure as `Err` and can reject other causes;
`runExit` preserves every cause for the boundary to inspect.

Add `Clock`, `Retry.policy`, and scoped Fibers when the workflow needs
time control, resilience, or concurrent children. `Retry.policy` works across both
`ResultAsync` and `ResultTask` call styles. Renaming
deprecated APIs is a separate, optional step and keeps their original behavior.

## Existing workflows

`ResultTask.succeed`, `fail`, `mapError`, `flatMap`, `andThen` and `catchAll` keep their instance and
static forms. Matching accepts `{ ok, err }` as well as `{ ok, error }` (and `{ onSuccess, onFailure }` on tasks).

Old spellings remain callable with the same behavior and are annotated
`@deprecated`. Adoption can happen gradually:

| Supported deprecated API | Equivalent preferred API |
| --- | --- |
| Task `succeed` / `fail` | `ResultTask.ok` / `ResultTask.err` |
| Task `mapError` / `flatMap` / `catchAll` | `mapErr` / `andThen` / `orElse` |
| Synchronous `Result` `tap` / `tapError` | `inspect` / `inspectError` |
| `safeTry` | `Result.gen` with plain success returns and `yield*` for Results/errors |
| `result.safeUnwrap()` | `yield* result` |
| `ResultAsync.fromTask(task)` | `ResultTask.toResultAsync(task)` |
| default, `try`, `tryCatch` | `tryResult` |
| `tryAsync`, `tryCatchAsync` | `tryResultAsync` |

Synchronous `Result` `tap` / `tapError` remain best-effort observation: callback
failures are swallowed and the original outcome is preserved. On `ResultTask` / `ResultAsync`,
`tap` / `tapError` / `tapBoth` keep their effectful composition behavior (propagating returned task
failures or thrown defects), while `inspect` / `inspectError` / `inspectBoth` provide best-effort
observation for logging and metrics across `Result`, `ResultAsync`, and `ResultTask`.

`Result.gen` now uses plain success returns: `return value` becomes `Ok(value)`, and
fallible steps or early errors short-circuit via `yield*` (`return yield* err(...)` or
`return yield* step()`). Returning a `Result`, `ResultAsync`, `Promise` (in sync
generators), or `ResultTask` directly from `Result.gen` is rejected at compile time. Sync
generators still return `Result` immediately; async generators return `ResultAsync`.
`safeTry` retains its original signatures and runtime behavior requiring a final `Result`
or `ResultAsync`. `safeUnwrap`, `SafeTryOptions` and `SafeTryAsyncOptions` remain
available. `ResultTask.gen` keeps its plain success return and lazy execution.

```ts
const createUser = (input: Input) => Result.gen(function* () {
  const email = yield* validateEmail(input.email)
  return yield* insertUser(email)
})
```

The default export, `try`, `tryCatch`, `tryAsync`, `tryCatchAsync` and
`ResultAsync.fromTask` remain supported. Existing checker rule IDs and
configuration options keep their names.

## Type safety improvements

Tagged recovery tables remove an error only when its handler is required and
defined in every possible table variant. Optional handlers keep the error in `E`;
recovery outputs include all possible handler returns. Code that relied on errors
being incorrectly erased may need to handle those errors explicitly.

New concurrent operations can produce `Cause.Parallel`. Consumers that inspect
Cause with an exhaustive switch should handle this branch alongside Sequential.
Existing sequential workflows retain their execution behavior.

## Matching at native HTTP boundaries

On `Result<T, E>`, `match`, `matchTags`, `matchTagsPartial`, and `unwrapOr` return the unwrapped
output `Out` directly. On `ResultAsync<T, E>` / `ResultTask<T, E, R>`, they are lazy task operators
returning `ResultTask<Out, never, R>` (which resolves to `Ok(Out)` when awaited, or `Out` via
`ResultTask.runPromise` / `.unwrapOrThrow()`, or you can `await` the task first to match on the
resolved `Result<T, E>`).
Partial fallbacks receive only errors not guaranteed to have a handler. Optional
handlers or handlers that can be undefined never erase a possible fallback error.
The special `Error` handler retains its existing runtime catch-all behavior.

`Match.context<Input, [context: Context]>()` compiles a function `(input, context)`
whose handlers receive `(narrowedInput, context)`. It avoids duplicating the
matched input in selector arguments. Native response/status unions are retained.
`Match.fn(selector)` keeps its existing selection and original-arguments contract.

Finite object patterns subtract combinations of literal fields, including nested
fields. Arbitrary predicates, partial refinements, optional patterns and open
arrays remain conservative. Exhaustive-call diagnostics expose `missingCases`.

## Task concurrency and policies

`forkChild` starts a child only during execution. Children belong to the enclosing
scope; closing it interrupts active children and awaits them before releasing
parent resources. `Fiber.join` propagates the child result. `Fiber.interrupt`
awaits completion and returns its full Exit. Unobserved child failures remain
tracked in the scope requirements and are included at closure.

`race` returns the first success; if both fail it preserves their parallel causes.
`raceFirst` returns the first outcome. Both interrupt remaining children and await
their finalizers. `timeout` uses a typed timeout error and the same cleanup rules.
Cleanup failures are preserved rather than being replaced by the winner.

```ts
const resilient = loadUser(id)
  .retry({ times: 2, delayMs: 100, backoff: 2, jittered: true })
  .timeout(2_000, () => new UserTimeoutError())

const result = await ResultTask.runResult(resilient)
```

`times` counts retries after the initial attempt. Retry applies only to simple
typed failures and closes each attempt scope before the next attempt. Defects,
interruption and composite failures are not retried. The optional `while` callback
filters retryable errors.

`all` preserves tuple/record shape; `forEach` preserves input order. Both default
to sequential execution and accept `{ concurrency: number | 'unbounded' }`.
Failure stops scheduling, interrupts active children and awaits their cleanup.
`validateAll` gathers typed errors in input order; defects and interruption stop it.

Cancellation remains cooperative. A task/driver that ignores abort, or a finalizer
that never settles, can keep the run pending. Timeout is not a hard deadline for
cleanup. `runExit` preserves `Parallel` and `Sequential` causes; `runResult`
rejects composite failures with ResultTaskCauseError.

## Deterministic time

Run options accept `clock?: TaskClock`; the default is `Clock.live`. Tests can
advance `Clock.virtual()` without wall-clock timers. Retry jitter uses the same
clock's random source, which can also be deterministic.

```ts
const clock = Clock.virtual()
const pending = ResultTask.runResult(task, { clock })
await clock.advanceBy(2_000)
const result = await pending
```

## Checker support

The checker recognizes both `safeTry` and `Result.gen` using the existing
`noAwaitInSafeTry`, `noTryCatchInSafeTry` and `yieldStarInSafeTry` options and their
original rule IDs. Delegated `yield*` expressions consume their Results, and the
new task collection/fiber operators are recognized as consumers. MatchMatcher
hover shows input, remaining cases and matched output.
